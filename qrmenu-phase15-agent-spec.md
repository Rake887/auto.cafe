# QR-Menu — Фаза 1.5 (v2): экономия на списаниях, навынос/доставка с защитой, база под аналитику

> Этот файл — ПРОДОЛЖЕНИЕ двух базовых спек:
> `qrmenu-mvp-agent-spec.md` (бэкенд) и `qrmenu-mvp-agent-spec-frontend.md` (фронтенд).
> Вставляй его агенту ПОСЛЕ того, как MVP по базовым спекам собран и работает.
> v2: Фича A заменена на модуль экономии (стоп-лист + прогноз заготовок),
> в Фичу B добавлен раздел защиты от фейковых заказов.

## 0. Зачем эти фичи (бизнес-контекст, коротко)

Владелец кафе покупает не «удобство для гостей», а деньги. Фудкост — ~30%
расходов заведения, списания и перезаготовки — постоянная утечка маржи,
агрегаторы доставки берут 15–35% комиссии.

- **Фича A (экономия на списаниях)** — стоп-лист в один тап + ежедневный
  прогноз заготовок: меньше выброшенной еды, меньше конфликтов «этого нет».
- **Фича B (навынос/доставка)** — своя ссылка на заказ без комиссии
  агрегаторов, теперь с защитой от фейковых заказов.
- **Фича C (данные)** — фундамент будущего аналитического модуля.

## 1. Что сознательно НЕ входит (не предлагать)

- Онлайн-оплата (Kaspi API и т.п.) — оплата на месте/при получении
- Интеграция с POS (Poster/iiko/r_keeper)
- ML/нейросети — только простые средние по дню недели
- SMS-верификация номера (дорого; подтверждение звонком сотрудника дешевле)
- CAPTCHA-сервисы — вместо них rate limiting
- Полный аналитический дашборд, лояльность, промокоды, i18n, трекинг курьера

## Фича A — Модуль экономии: стоп-лист + прогноз заготовок

Обе части работают через уже существующий Telegram-бот. Нового UI — минимум.

### A.1 Стоп-лист в один тап (работает с первого дня)

Проблема: блюдо закончилось, а гости продолжают заказывать его через QR —
официант ходит извиняться, заказ переделывают, время и лояльность сгорают.

Бэкенд:
- [ ] `dish.is_stopped bool default false`
- [ ] Команда бота `/stop` — бот отвечает списком активных блюд кнопками,
      тап по блюду ставит `is_stopped = true` и мгновенно убирает его из меню.
      Команда `/unstop` — то же самое в обратную сторону.
- [ ] `GET /m/{token}` и `GET /p/{slug}` не отдают блюда со стопом.
- [ ] Серверная валидация: `POST /orders` отклоняет позиции из стоп-листа
      с понятной ошибкой (гость мог открыть меню ДО того, как блюдо застопили).

Фронтенд:
- [ ] Обработать ошибку «блюдо закончилось» при оформлении: показать какие
      позиции убрать, не терять остальную корзину.

Критерий готовности: повар застопил блюдо через бота → в открытом меню оно
пропадает при обновлении → попытка оформить заказ со старой корзиной даёт
понятное сообщение, корзина не ломается.

### A.2 Прогноз заготовок (включается после накопления данных)

Проблема: заготовки делают «на глаз» → перезаготовка → списания. Прогноз
даже простыми средними сокращает выброшенную еду.

Бэкенд:
- [ ] Роль `owner` в `staff` (регистрация через тот же invite-механизм).
- [ ] Management-команда `python -m app.digest`, запускаемая планировщиком
      (cron/systemd timer в docker-окружении; Celery НЕ вводить):
      каждый вечер отправляет owner'у в Telegram дайджест:
      — по каждому активному блюду: среднее число порций в ЗАВТРАШНИЙ день
        недели за последние 4 недели + продано сегодня;
      — блюда-аутсайдеры недели (кандидаты на вывод из меню — это тоже
        экономия закупок).
- [ ] Если данных меньше 14 дней — дайджест пишет «копим статистику, прогноз
      появится ДД.ММ», не показывает мусорные цифры.
- [ ] Простые средние по дню недели. Никаких ML, погоды, праздников.

Критерий готовности: на тестовых данных за 3+ недели команда шлёт owner'у
осмысленный дайджест; при пустой базе — честное «копим статистику».

## Фича B — Своя страница навынос / доставки

### B.1 Модель данных (бэкенд)

- [ ] `order.type` enum: `dine_in | pickup | delivery`. Существующие заказы
      через QR стола = `dine_in` (default), миграция без потери данных.
- [ ] Поля заказа (nullable, для pickup/delivery): `customer_name`,
      `customer_phone` (обязателен для pickup/delivery, серверная валидация
      формата +7 7XX XXX XX XX), `delivery_address` (обязателен только для
      delivery), `desired_time` (пусто = «как можно быстрее»).
- [ ] `branch.slug UNIQUE` — публичная ссылка `/p/{slug}`, задаётся в сидинге.
- [ ] `branch.pickup_enabled bool`, `branch.delivery_enabled bool`.

### B.2 API (бэкенд)

- [ ] `GET /p/{slug}` — то же меню, что `/m/{token}`, но без стола; в ответе
      флаги `pickup_enabled` / `delivery_enabled`.
- [ ] `POST /orders` расширить: `type`, контактные поля, `branch_slug`
      (pickup/delivery) ИЛИ `point_token` (dine_in) — ровно одно из двух.
- [ ] Идемпотентность через `client_request_id` — как в MVP.

### B.3 Статусы и Telegram-бот

Цепочка статусов: `new → confirmed → accepted → ready → served → cancelled`.
Для `dine_in` шаг `confirmed` пропускается (new → accepted напрямую).

- [ ] Сообщение о заказе помечать типом: «🍽 Стол 5» / «🥡 Навынос, к 18:30,
      +7 7XX…» / «🛵 Доставка, адрес…».
- [ ] Для pickup/delivery первое сообщение содержит кнопки
      [Подтвердить] / [Отклонить] (см. B.6). После подтверждения — обычная
      цепочка [Принял] → [Готово] → [Выдан/Передан курьеру].
- [ ] [Отклонить] → статус `cancelled`, гостю на экране статуса — «заказ не
      подтверждён, позвоните заведению: <телефон>».

### B.4 Фронтенд

- [ ] Маршрут `/p/[slug]` — переиспользует ВСЕ компоненты меню и корзины.
- [ ] Оформление pickup: имя + телефон + желаемое время.
      Оформление delivery: то же + адрес.
- [ ] Переключатель «Навынос / Доставка» только если включены оба режима.
- [ ] Экран статуса: для pickup/delivery добавить состояние «ждёт
      подтверждения — вам перезвонят», подписи по типу заказа
      («Можно забирать!» вместо «Готово, несём»).

### B.5 Критерий готовности

По ссылке `/p/{slug}` оформляется заказ навынос; в Telegram приходит «🥡» с
[Подтвердить]/[Отклонить]; после подтверждения полный цикл до «Выдан»;
заказы со столов работают как раньше, без шага подтверждения.

### B.6 Защита от фейковых заказов (обязательный раздел)

Угроза: злоумышленник оформляет навынос/доставку и не приходит — еда
приготовлена впустую. Защита слоями:

- [ ] **Подтверждение звонком (главный слой).** Заказ pickup/delivery НЕ идёт
      на кухню, пока сотрудник не перезвонил по указанному номеру и не нажал
      [Подтвердить]. `branch.require_confirmation bool default true` —
      заведение может отключить, если доверяет потоку.
- [ ] **Чёрный список номеров.** Таблица
      `phone_blocklist (id, branch_id, phone, reason, created_at)`.
      На финальном шаге pickup/delivery рядом с [Выдан] — кнопка [Не забрал]:
      статус `cancelled` + счётчик невыкупов по номеру. После 2 невыкупов
      (константа в конфиге) номер автоматически попадает в blocklist.
      `POST /orders` для номера из blocklist — вежливый отказ: «онлайн-заказ
      недоступен, позвоните заведению напрямую».
- [ ] **Лимит активных заказов**: не больше 2 незавершённых
      (не `served`/`cancelled`) заказов на один номер телефона одновременно.
- [ ] **Rate limiting** на `POST /orders` по IP (например, slowapi:
      5 заказов / 10 минут с одного IP) — защита от спама ботами.
      Отдельно лимит на `GET /p/{slug}` не нужен.
- [ ] **Серверная валидация телефона** — фронтовая маска не считается защитой.
- [ ] В README — заметка для владельцев: для крупных заказов при
      подтверждающем звонке можно попросить предоплату переводом Kaspi по
      номеру. Это процесс заведения, НЕ функциональность кода — не строить.

Заметь: для `dine_in` защита не нужна — гость физически сидит в зале.

Критерий готовности: заказ с номера из blocklist отклоняется; третий
одновременный заказ с одного номера отклоняется; спам ботом в POST /orders
режется rate limit'ом; [Не забрал] дважды → номер в blocklist автоматически.

## 2. Порядок работ и правила

1. **A.1 Стоп-лист** — самый маленький кусок, быстрый видимый результат для демо.
2. **Фича B целиком, включая B.6** — главный питч-аргумент («без комиссии
   агрегаторов, с защитой от фейков»).
3. **Фича C** — эндпоинты статистики и дисциплина логирования.
4. **A.2 Прогноз заготовок** — последним: ему нужны накопленные данные,
   а слой статистики из C он переиспользует.

Правила — те же, что в базовых спеках:
- async SQLAlchemy, Pydantic-схемы на каждый ответ (OpenAPI — контракт)
- Не переусложнять: никаких Celery/очередей/кэшей; планировщик — cron/systemd
- После каждой фичи — пауза: резюме, что проверить руками, вопросы если
  что-то неоднозначно
- Миграции Alembic — обратимые, существующие данные MVP не ломать
