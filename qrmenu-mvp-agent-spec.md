# QR-Menu MVP — техническое задание для агента (бэкенд, FastAPI)

> Вставь этот файл первым сообщением в чат с кодинг-агентом (Claude Code и т.п.) —
> так у него сразу будет весь контекст задачи и он сможет работать по этапам.

## 1. Контекст проекта

Строим MVP-демо SaaS QR-меню для кафе Тараза (Казахстан). Цель — рабочий прототип
для демонстрации владельцам кафе, НЕ финальный продукт.

**Сценарий целиком:**
Гость сканирует QR на столе → открывает меню на сайте → собирает корзину →
оформляет заказ → заказ уходит в Telegram-группу заведения → повар видит заказ,
жмёт «Принял», потом «Готово» → официант видит что заказ готов и на каком столе,
жмёт «Обслуживаю» → всё, цикл завершён.

**Разделение работы:** я (бэкенд, Python/FastAPI) + друг (фронтенд, React).
Друг работает по OpenAPI-схеме, которую отдаёт FastAPI автоматически (`/docs`).

**Важно — что НЕ входит в этот MVP** (сознательно упрощено относительно полного
продукта):
- Нет оплаты (Kaspi/Halyk и т.д.)
- Нет интеграции с POS (Poster/iiko/r_keeper)
- Нет мультиарендности «на продакшн уровне» — одно кафе захардкожено
- Нет i18n (только русский)
- Нет модификаторов блюд, стоп-листов, ролей owner/manager
- Нет отдельного веб-экрана кухни — только Telegram-бот

Всё перечисленное выше — сознательно отложено, не предлагай это добавить,
если явно не попросят.

## 2. Технический стек

- **Backend:** Python 3.12+, FastAPI, SQLAlchemy 2.0 (async), Alembic (миграции)
- **DB:** PostgreSQL 16
- **Bot:** aiogram 3.x (Telegram Bot API), режим webhook (не polling)
- **Инфраструктура:** Docker Compose для локальной разработки
- **Package manager:** uv или poetry (на выбор агента, зафиксировать один)

## 3. Схема базы данных (упрощённая для MVP)

```
organization (id, name)
branch (id, organization_id, name)
point (id, branch_id, label, token UNIQUE)       -- QR-токен стола/кабинки
category (id, branch_id, name, sort_order)
dish (id, category_id, name, price, image_url, is_active)
"order" (id, branch_id, point_id, status, created_at, client_request_id UNIQUE)
    -- status enum: new -> accepted -> ready -> served -> cancelled
order_item (id, order_id, dish_id, qty, price_snapshot, dish_name_snapshot)
staff (id, branch_id, telegram_chat_id, role, full_name)
    -- role enum: cook, waiter
order_status_log (id, order_id, from_status, to_status, actor_telegram_id, at)
```

**Обязательные детали:**
- `point.token` — случайная непубличная строка (НЕ последовательный id), уникальный индекс
- `order.client_request_id` — UUID от клиента, уникальный индекс — защита от дублей
  при повторном тапе «Оформить заказ» на плохом интернете
- `order_item.price_snapshot` и `dish_name_snapshot` — сохраняем цену и название
  на момент заказа (цена блюда может измениться позже, история заказа не должна ехать)
- Один `organization_id` захардкожен в конфиге для демо (одно кафе), но модель
  всё равно многоарендная по структуре — не хардкодь id прямо в SQL-запросах

## 4. Этапы разработки

Работай строго по этапам. После каждого этапа — короткое резюме что сделано
и что можно проверить руками (curl/Postman/`/docs`), прежде чем переходить дальше.

---

### Этап 1 — Каркас проекта

- [ ] Инициализировать FastAPI-проект, структура папок:
  ```
  app/
    main.py
    core/          # config, db session
    models/        # SQLAlchemy модели
    schemas/       # Pydantic схемы
    api/           # роутеры: menu, orders, telegram
    services/      # бизнес-логика
    bot/           # aiogram handlers
  alembic/
  docker-compose.yml
  .env.example
  ```
- [ ] `docker-compose.yml`: сервисы `api` (FastAPI) + `db` (Postgres)
- [ ] Настроить async SQLAlchemy engine + сессии через dependency injection
- [ ] Настроить Alembic, сгенерировать первую миграцию по схеме из раздела 3
- [ ] `GET /health` —健康check эндпоинт

**Критерий готовности:** `docker-compose up` поднимает API и БД, миграции
применяются, `/health` отвечает 200.

---

### Этап 2 — Сидинг демо-данных

- [ ] Скрипт `seed.py`, который создаёт:
  - 1 organization, 1 branch
  - 3-5 point (столов) с уникальными токенами
  - 3-4 category, 10-15 dish с ценами и заглушками картинок
- [ ] Скрипт запускается командой типа `python -m app.seed`

**Критерий готовности:** после сидинга в БД есть тестовое кафе с меню, можно
достать токен любого стола для дальнейшего тестирования.

---

### Этап 3 — Гостевое API (меню и корзина)

- [ ] `GET /m/{token}` — вернуть данные филиала + список категорий с блюдами
      по токену стола. 404 если токен не найден.
- [ ] Схема ответа должна быть удобной для фронта — не заставлять React
      делать дополнительные запросы за категориями отдельно от блюд
- [ ] Валидация на сервере: цены НЕ принимать от клиента, только id блюд +
      количество — сервер сам подставляет актуальную цену из БД

**Критерий готовности:** по токену стола отдаётся полное меню одним запросом.

---

### Этап 4 — Оформление заказа

- [ ] `POST /orders` — тело: `{point_token, client_request_id, items: [{dish_id, qty}]}`
- [ ] Идемпотентность: если `client_request_id` уже существует — вернуть
      существующий заказ, не создавать дубль (важно проверить конкурентный сценарий)
- [ ] Посчитать сумму на сервере (никогда не доверять сумме от клиента)
- [ ] После создания заказа — вызвать сервис отправки уведомления в Telegram
      (см. Этап 6)
- [ ] `GET /orders/{id}` — статус заказа, для поллинга с фронта (гость видит
      «Готовим» / «Готово»)

**Критерий готовности:** можно оформить заказ через API, повторный запрос
с тем же `client_request_id` не создаёт второй заказ.

---

### Этап 5 — Регистрация персонала в боте

- [ ] `POST /staff/invite` — генерирует одноразовый токен приглашения для
      сотрудника (роль cook/waiter, имя)
- [ ] Bot handler на `/start <token>` — сверяет токен, сохраняет
      `telegram_chat_id` сотрудника в БД, подтверждает регистрацию сообщением

**Критерий готовности:** по сгенерированной ссылке `t.me/bot?start=<token>`
сотрудник регистрируется, chat_id сохраняется в БД.

---

### Этап 6 — Telegram-бот: поток заказа

- [ ] При создании заказа (Этап 4) — отправить сообщение в общий чат заведения:
      состав заказа, номер стола, кнопка `[Принял]`
- [ ] Webhook `/telegram/webhook` принимает апдейты от Telegram
- [ ] `callback_query` на `[Принял]`:
      - статус заказа → `accepted`
      - редактировать исходное сообщение (убрать кнопку, показать кто принял)
      - записать в `order_status_log`
      - добавить кнопку `[Готово]`
- [ ] `callback_query` на `[Готово]`:
      - статус → `ready`
      - отправить НОВОЕ сообщение в чат: «Заказ готов, стол №X» с кнопкой
        `[Обслуживаю]`
- [ ] `callback_query` на `[Обслуживаю]` (нажимает официант):
      - статус → `served`
      - редактировать сообщение, показать кто забрал

**Критерий готовности:** полный цикл заказа проходит через бота от создания
до `served`, статусы корректно меняются, история пишется в `order_status_log`.

---

### Этап 7 — Настройка вебхука и деплой для демо

- [ ] Инструкция/скрипт для `setWebhook` при старте приложения
- [ ] `.env.example` со всеми нужными переменными (DB_URL, BOT_TOKEN, WEBHOOK_URL)
- [ ] Простой README: как поднять локально, как прогнать сценарий целиком
      руками (curl-примеры для каждого шага)

**Критерий готовности:** человек с нуля может поднять проект по README и
пройти весь сценарий от скана QR (условно — прямого GET по токену) до
получения заказа официантом.

## 5. Правила работы для агента

- Пиши async-код везде, где взаимодействие с БД — используется async SQLAlchemy
- Каждый эндпоинт — с Pydantic-схемой ответа, чтобы FastAPI сгенерировал
  корректный OpenAPI (это контракт для фронтендера)
- Не переусложняй сверх ТЗ — если кажется что нужен паттерн Repository/Unit of
  Work/DDD-слои — не надо, это MVP на одного бэкендера
- Пиши базовые docstring на функции, но не переусердствуй с комментариями
- После каждого этапа — можно приостановиться и спросить, продолжать ли, если
  что-то в ТЗ показалось неоднозначным, вместо того чтобы додумывать самому
- Токены (`point.token`, invite-токены) — генерировать через `secrets.token_urlsafe`,
  не через предсказуемые UUID4 если это влияет на угадываемость
