# QR-Menu MVP — техническое задание для агента (фронтенд, Next.js)

> Вставь этот файл первым сообщением в чат с кодинг-агентом (Claude Code и т.п.) —
> так у него сразу будет весь контекст задачи. Это парный документ к бэкенд-спеке
> (`qrmenu-mvp-agent-spec.md`) — API-контракт между ними должен совпадать.

## 1. Контекст проекта

Гостевой фронтенд для QR-меню кафе в Таразе (Казахстан). Гость сканирует QR на
столе → попадает на этот сайт → смотрит меню → собирает корзину → оформляет
заказ → видит статус («Готовим» → «Готово»).

**Это демо-MVP для показа владельцам кафе, не финальный продукт.** Не
переусложняй сверх ТЗ.

**Кто делает бэкенд:** партнёр на FastAPI. API уже спроектировано (см. раздел 3
ниже), бэкенд может быть ещё не готов на момент старта фронтенд-работы —
закладывай мок-данные там, где реального API пока нет.

**Что сознательно НЕ входит в MVP:**
- Нет оплаты онлайн
- Нет личного кабинета/логина гостя
- Нет мультиязычности (только русский на старте)
- Нет админки для официанта/повара — у них отдельный интерфейс, это Telegram-бот
  (не часть этого фронтенда)
- Нет push-уведомлений — статус заказа гость видит через поллинг на странице

Не предлагай добавить перечисленное, если явно не попросят.

## 2. Технический стек и ключевые принципы

- **Framework:** Next.js (App Router), SSR/ISR — НЕ чистый SPA
- **Стилизация:** Tailwind CSS v4 + CSS custom properties (дизайн-токены)
- **Язык:** TypeScript
- **State:** минимально — корзина в React state/context, без Redux/Zustand
  для MVP (не усложняй)

**Почему SSR/ISR, а не SPA:** целевая аудитория — гости кафе в Таразе на
мобильном интернете, часто не 4G/5G. Чистый React SPA (Vite) даёт 200-400 КБ
JS и 3-6 секунд белого экрана до первого контента — неприемлемо. Меню должно
рендериться на сервере и быть видно почти сразу.

**Целевые метрики скорости:**
- Контент виден до **1.5 сек на 4G**
- От скана QR до отправленного заказа — **не больше 3 тапов**

**Приёмы для скорости (обязательны, не опциональны):**
- Кнопка «+» добавления в корзину прямо в списке блюд, без захода в карточку
- Корзина — нижняя шторка (bottom sheet), не отдельная страница
- Системные шрифты по умолчанию, кастомные шрифты — только если реально нужны
  под дизайн-токены (см. раздел 5), без лишних Google Fonts россыпью
- Инлайн-SVG для иконок вместо иконочных библиотек (react-icons и т.п. — не тащить
  ради 3 иконок)
- Скелетоны (skeleton loaders) вместо спиннеров при загрузке
- Липкие (sticky) табы категорий при скролле меню

## 3. API-контракт (согласовано с бэкендом)

Бэкенд на FastAPI отдаёт автодокументацию на `/docs`, но вот базовый контракт
для старта работы до готовности бэкенда:

### `GET /m/{token}`
Возвращает меню филиала по токену стола.
```json
{
  "branch_name": "string",
  "point_label": "Стол 5",
  "categories": [
    {
      "id": 1,
      "name": "Горячие блюда",
      "dishes": [
        {
          "id": 10,
          "name": "Плов",
          "price": 2500,
          "image_url": "https://..." 
        }
      ]
    }
  ]
}
```

### `POST /orders`
Тело запроса:
```json
{
  "point_token": "string",
  "client_request_id": "uuid-v4-сгенерированный-на-клиенте",
  "items": [{ "dish_id": 10, "qty": 2 }]
}
```
Ответ: `{ "order_id": 123, "status": "new" }`

**Важно:** `client_request_id` генерируется на фронте один раз при открытии
корзины (не при каждом клике «Оформить») — если пользователь тапнет кнопку
дважды из-за плохого интернета, бэкенд не создаст дубль заказа.

### `GET /orders/{id}`
Для поллинга статуса. Ответ: `{ "id": 123, "status": "new|accepted|ready|served" }`

Опрашивать раз в 3-5 секунд, прекратить опрос при статусе `served`.

## 4. Экраны и пользовательский сценарий

```
[Скан QR] → /m/{token}
    ↓ (тап 1: добавить блюдо в корзину прямо из списка)
[Список блюд по категориям, липкие табы сверху]
    ↓ (тап 2: открыть корзину — нижняя шторка)
[Корзина: список позиций, количество, сумма]
    ↓ (тап 3: «Оформить заказ»)
[Экран статуса заказа: "Заказ принят" → "Готовим" → "Готово!"]
```

Итого 3 тапа от открытия ссылки до отправленного заказа — это KPI, не
превышать.

## 5. Дизайн-система

### 5.1 Принцип
Деловой элегантный минимализм — НЕ аскетичный голый список. Сдержанная
премиальность: приглушённая палитра, много воздуха, аккуратная типографика.

### 5.2 Токены (для MVP — один пресет, не все семь)
Для демо-версии реализуй **один пресет** (выбери «Кофейня» — самый универсальный
для показа разным типам заведений), остальные шесть — не делать в MVP, это
Фаза 2:

```css
--color-surface: #FBF7F0;
--color-text: #2A211B;
--color-accent: #A6633B;
--font-heading: 'Fraunces', serif;
--font-body: 'Manrope', sans-serif;
```

Двухслойная система: примитивы (`--gray-100`, `--brand-500` и т.п.) →
семантические токены (`--color-surface`, `--color-primary`). Компоненты в коде
используют **только** семантические токены, никогда примитивы напрямую — это
то, что позволит потом легко добавить остальные 6 пресетов без переписывания
компонентов.

### 5.3 Шрифты — важное ограничение
Если для полного продукта потребуется поддержка казахского языка — шрифт
обязан корректно рисовать глифы `ә ғ қ ң ө ұ ү һ і`. Для MVP (русский
интерфейс) это не критично, но выбирай из шрифтов с проверенной поддержкой на
будущее: **Inter, Manrope, PT Sans/Serif, Golos Text, Montserrat, Rubik,
Nunito Sans** — не бери шрифт из непроверенных, если он не в этом списке.

## 6. Работа с изображениями

- Превью в списке блюд: **80×80 WebP**, ленивая загрузка (`loading="lazy"`)
- Крупное фото — по тапу на блюдо (не обязательно для MVP, можно отложить)
- Next.js `<Image>` компонент — не `<img>` напрямую, чтобы получить
  автоматическую оптимизацию и lazy loading из коробки

## 7. Этапы разработки

Работай строго по этапам. После каждого — короткое резюме что сделано и что
можно проверить руками в браузере.

---

### Этап 1 — Каркас проекта

- [ ] Инициализировать Next.js (App Router, TypeScript, Tailwind v4)
- [ ] Настроить дизайн-токены из раздела 5.2 как CSS custom properties
- [ ] Базовый layout, системные шрифты по умолчанию
- [ ] Заглушка страницы `/m/[token]` — статичный текст, просто чтобы роутинг работал

**Критерий готовности:** `npm run dev` поднимает проект, страница
`/m/test-token` открывается.

---

### Этап 2 — Мок-данные и структура меню

- [ ] Создать мок-JSON, повторяющий структуру ответа `GET /m/{token}`
      (раздел 3) — чтобы верстать не дожидаясь готовности бэкенда
- [ ] Типизировать через TypeScript (interface `MenuResponse`, `Category`, `Dish`)
- [ ] Слой абстракции для загрузки данных (функция `fetchMenu(token)`) —
      чтобы потом легко переключить с мока на реальный fetch к бэкенду одним
      местом в коде, не по всему проекту

**Критерий готовности:** страница меню рендерит мок-данные через типизированную
структуру, легко читаемую точку переключения на реальный API видно в коде.

---

### Этап 3 — Экран меню

- [ ] Список категорий с липкими (sticky) табами сверху при скролле
- [ ] Список блюд по категориям — карточка: фото 80×80, название, цена,
      кнопка «+» прямо в списке
- [ ] Скелетоны при начальной загрузке (не спиннер)
- [ ] Пустое состояние (если категория без блюд) и состояние ошибки
      (невалидный токен стола → понятное сообщение, не белый экран)

**Критерий готовности:** меню визуально готово, скроллится, табы прилипают,
добавление в корзину визуально откликается (даже если корзина пока не готова
как компонент).

---

### Этап 4 — Корзина (нижняя шторка)

- [ ] React state/context для корзины (без внешних библиотек стейт-менеджмента)
- [ ] UI нижней шторки: список позиций, +/- количество, удаление позиции, сумма
- [ ] Генерация `client_request_id` (UUID v4) при первом открытии корзины,
      хранится в state до момента успешной отправки заказа
- [ ] Кнопка «Оформить заказ» — задизейблена, если корзина пуста

**Критерий готовности:** можно добавлять/убирать блюда, корзина считает сумму
верно, `client_request_id` генерируется один раз и не пересоздаётся при
случайных ре-рендерах.

---

### Этап 5 — Отправка заказа и экран статуса

- [ ] Обработчик «Оформить заказ» → `POST /orders` (или мок, если бэкенд
      ещё не готов — сделать mock-функцию с той же сигнатурой)
- [ ] После успешной отправки — редирект/переход на экран статуса заказа
- [ ] Экран статуса: поллинг `GET /orders/{id}` раз в 3-5 секунд
- [ ] Визуальные состояния: `new` → «Заказ принят», `accepted` → «Готовим»,
      `ready` → «Готово!», `served` → остановить поллинг, финальный экран
- [ ] Обработка сетевых ошибок при отправке заказа — понятное сообщение +
      возможность повторить (используя тот же `client_request_id`, не новый)

**Критерий готовности:** полный сценарий от меню до экрана «Готово» проходим
руками на мок-данных, поллинг корректно останавливается на финальном статусе.

---

### Этап 6 — Полировка скорости и мобильного UX

- [ ] Проверить реальные метрики загрузки (Lighthouse/Chrome DevTools на
      throttling 4G) — контент должен быть виден до 1.5 сек
- [ ] Убедиться что нет лишних тяжёлых зависимостей в бандле (проверить
      `next build` вывод по размеру)
- [ ] Проверить на реальном мобильном устройстве, не только в браузере
      десктопа с эмуляцией
- [ ] touch-friendly размеры кнопок (не мельче 44×44px — стандарт для тапа
      пальцем)

**Критерий готовности:** сценарий проходится с телефона, ощущается быстрым,
ничего не «прыгает» при загрузке (не забыть зарезервировать место под картинки
чтобы не было layout shift).

## 8. Правила работы для агента

- Не добавляй библиотеки состояния (Redux/Zustand/Jotai) для MVP — React
  Context достаточно для корзины такого размера
- Не строй дизайн-систему на все 7 пресетов сразу — только «Кофейня» из
  раздела 5.2, остальное — Фаза 2, не предлагай делать сейчас
- Мок-слой (Этап 2) обязателен — не жди готовности бэкенда, чтобы начать
  вёрстку
- Если что-то в API-контракте (раздел 3) кажется неудобным для фронта —
  предложи изменение и спроси, а не решай сам менять формат ответа без
  согласования (это совместный контракт с бэкенд-частью)
- Мобильный экран — приоритет №1. Десктопная адаптация не нужна для MVP
  (гости сканируют QR телефоном, десктоп-версия не входит в сценарий)
