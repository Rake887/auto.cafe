# QR-Menu MVP

Демо SaaS QR-меню для кафе в Таразе. Полный цикл: гость сканирует QR на столе →
меню в браузере → корзина → заказ → уведомление в Telegram-группу заведения →
повар «Принял» → «Готово» → официант «Обслуживаю».

| Часть | Папка | Стек | Порт на хосте |
|---|---|---|---|
| Гостевой фронтенд | [frontend/](frontend/) | Next.js 16 (App Router, SSR), TypeScript, Tailwind v4 | 3000 |
| Бэкенд + Telegram-бот | [backend/](backend/) | FastAPI, SQLAlchemy 2.0 async, aiogram 3 | 8010 |
| PostgreSQL 16 | — | образ `postgres:16-alpine` | 55433 |

Подробности по каждой части — в [backend/README.md](backend/README.md) и
[frontend/README.md](frontend/README.md).

## Запуск целиком

```bash
cp .env.example .env
docker compose up -d --build
docker compose --profile tools run --rm seed   # демо-меню и столы, один раз
```

Готово: `http://localhost:3000` — служебная страница со ссылкой на демо-стол,
`http://localhost:3000/m/demo` — то, что видит гость после скана QR,
`http://localhost:8010/docs` — Swagger бэкенда.

Миграции применяются сами при старте контейнера `api`, отдельной команды не
нужно. Сидинг идемпотентен: повторный запуск ничего не дублирует.

Полезное:

```bash
docker compose logs -f api        # логи бэкенда и бота
docker compose ps                 # статус и healthcheck всех сервисов
docker compose down               # остановить (данные в томе остаются)
docker compose down -v            # остановить и стереть базу
```

## Настройки (.env в корне)

Всё конфигурируется одним файлом, скопированным из
[.env.example](.env.example):

| Переменная | Зачем |
|---|---|
| `WEB_PORT`, `API_PORT`, `DB_PORT` | порты на хосте, если стандартные заняты |
| `PUBLIC_API_BASE` | путь к API для браузера гостя; по умолчанию `/api` — тот же origin, что и меню |
| `DEMO_TOKEN` | токен демо-стола: сидинг выдаёт его «Столу 1», фронтенд ставит в кнопку «Открыть демо-меню» |
| `BOT_TOKEN`, `WEBHOOK_URL`, `WEBHOOK_SECRET`, `GROUP_CHAT_ID` | Telegram; при пустом `BOT_TOKEN` бот просто выключен |
| `ADMIN_TOKEN` | машинный ключ к админ-API для curl и скриптов (`?token=`); люди входят по паролю |
| `ORDER_REMINDER_MINUTES` | через сколько минут бот напомнит о непринятом заказе; `0` выключает напоминания |
| `SERVICE_CALL_SLA_SECONDS` | через сколько секунд непринятый вызов официанта дёрнет чат повторно; `0` выключает эскалацию |
| `BOT_POLLING` | `1` — бот сам ходит за обновлениями (нужно локально), `0` — вебхук (для своего домена) |
| `POSTGRES_*` | учётные данные БД |

### Один origin вместо трёх адресов

Перед стеком стоит Caddy ([proxy/Caddyfile](proxy/Caddyfile)): `/` отдаёт
меню, `/api/*` уходит на FastAPI со срезанным префиксом. Поэтому браузер
ходит в API по относительному `/api` и не знает внешнего адреса вообще —
один и тот же образ работает на `localhost`, в локальной сети и через
туннель, без пересборки. CORS при этом не нужен: origin один.

SSR внутри docker-сети ходит напрямую в `http://api:8000`
(`INTERNAL_API_BASE` в compose), минуя прокси.

### Показ с телефона

Если телефон в той же сети — достаточно адреса машины: `http://192.168.0.10:3000`
(порт `WEB_PORT`), пересобирать ничего не надо.

Если сети разные, поднимите Cloudflare-туннель — он даёт публичный HTTPS
без страницы-предупреждения и не требует аккаунта:

```bash
docker compose --profile tunnel-cf up -d cloudflared
docker compose logs cloudflared | grep -o 'https://[a-z-]*\.trycloudflare\.com'
```

Полученный адрес открывается с любого телефона; меню будет на
`<адрес>/m/demo`.

## Наклейки на столы

`/admin/qr` — QR-коды столов в двух форматах под печать: наклейки 65×65 мм с
пунктиром реза и тейбл-тенты со сгибом. Под каждым кодом адрес сайта, лист A4,
карточки не рвутся между страницами. Печатать лучше на плотной бумаге и
ламинировать: под плёнкой код переживает уборку.

Адрес под кодом напечатан намеренно. Подмена наклейки чужим QR — известная
атака (quishing); напечатанный домен даёт гостю шанс заметить подлог.

Ссылки в кодах строятся от текущего публичного адреса, поэтому при
перезапуске туннеля их нужно перепечатать. Для постоянного адреса нужен свой
домен и именованный туннель Cloudflare.

## Кабинет владельца

Вход — `/admin/login` по логину и паролю. На чистой базе владельца ещё нет,
поэтому страница входа сама уводит на `/admin/setup` — форму первичной настройки.
Она живёт ровно до появления первого администратора, дальше отдаёт 404: иначе
доступ завёл бы себе любой желающий. Подключить заведение можно целиком из
браузера, без захода по SSH.

Запасной путь, если до кабинета не добраться, — консоль:

```bash
docker compose exec api python -m app.create_admin
```

Пароль там спрашивается интерактивно, аргументом его передать нельзя — иначе он
осел бы в истории команд. Пять неверных попыток подряд блокируют вход на
15 минут.

Пароль меняется в самом кабинете, `/admin/settings`. Смена гасит все прочие
сессии: если пароль подсмотрели, чужое устройство должно вылететь.

Разделы кабинета: статистика (`/admin`), меню (`/admin/menu`), заказы
(`/admin/orders`), вызовы (`/admin/calls`), отзывы (`/admin/reviews`), персонал
(`/admin/staff`), столы (`/admin/tables`), печать QR (`/admin/qr`) и настройки
(`/admin/settings`).

### Сейчас в зале

Первое, что видно на `/admin`, — не выручка за неделю, а то, что горит прямо
сейчас: сколько заказов не приняли (и сколько минут ждёт самый старый), сколько
готовят, сколько стоит готовыми, кто зовёт официанта, по каким столам не закрыт
счёт и сколько жалоб ждёт разбора. Блок обновляется сам раз в 15 секунд. Когда
всё спокойно, он так и пишет — «тихо», чтобы не создавать ложного ощущения работы.

Там же кнопка приёма заказов: во время наплыва или поломки на кухне владелец
выключает её в один тап, и гость видит «закрыто» ещё до того, как соберёт
корзину.

### Когда принимаем заказы

`/admin/settings` → часы приёма. Вне этих часов гость видит «Закрыто» вместо
кнопки корзины, а `POST /orders` отвечает 409 — заказать по сфотографированному
QR ночью не получится. Окно через полночь (22:00—02:00) считается правильно.
Пусто — принимаем круглосуточно.

Ещё одна защита — частота: больше пяти заказов с одного стола за десять минут
отклоняются с 429. Живой стол столько не оформляет, а вот скрипт по украденному
токену — сколько угодно.

### Заказ не из зала

Статический QR по своей природе работает у всех, кто его когда-либо видел:
наклейку могут сфотографировать, ссылку — переслать. Важно понимать, что при
этом теряется. Денег заведение не теряет — предоплаты нет, счёт приносит
официант. Теряется **приготовленная еда, которую никто не забрал**, и время
кухни. И теряется только если кухня успела начать готовить.

Поэтому барьер стоит не на приёме заказа, а **перед готовкой**. Пока за стол
никто не поручился, в чат приходит не «Принял», а «🪑 Гость за столом».
Официант поднимает глаза: если стол пуст, никто не нажимает, кухня не начинает,
потерь нет. Ручаются один раз на визит — следующие заказы того же стола идут
обычным порядком.

Чтобы живые гости этого шага не видели, присутствие определяется автоматически
по двум признакам, и хватает любого:

- **Wi-Fi заведения.** Если заказ пришёл с публичного IP заведения, гость сидит
  в зале. Признак сильный: подделать его снаружи нельзя. Настраивается в
  `/admin/settings` кнопкой «Мой IP» — нажимать нужно, **открыв кабинет по
  домену заведения с его Wi-Fi**.
- **Координаты в радиусе зала.** Работает для гостей на мобильном интернете,
  если они разрешили геолокацию.

Точку заведения задавайте **ссылкой на карточку в 2ГИС** (Яндекс Карты и Google
Maps тоже подойдут, как и просто пара координат): вставьте адрес в поле «Где
находится зал» и нажмите «Определить». Короткие ссылки из кнопки «Поделиться»
разворачиваются сами.

Кнопка «Взять с этого устройства» осталась, но годится, только если вы стоите
в зале **с телефоном**: у компьютера нет GPS, он определяет место по сети и
промахивается на километры, а из дома запишет координаты квартиры — тогда
проверка начнёт врать в обе стороны, помечая гостей в зале как «вне зала».

После разбора ссылки обязательно нажмите «Открыть на карте» и посмотрите, куда
встала точка. У 2ГИС и Яндекса в адресе сначала долгота, у Google — широта;
перепутанный порядок не даёт ошибки, потому что числа остаются валидными, и
ловится он только глазами.

Подтверждать вручную придётся только тому, кто и на мобильном, и отказал в
доступе к геолокации — один тап за визит.

Заказ с координатами **вне** радиуса всё равно принимается, но помечается «вне
зала» в чате и в ленте. Жёстко блокировать по геолокации нельзя: в помещении GPS
врёт на сотни метров, и отказ получили бы живые люди за столом.

Две технические тонкости, о которые легко разбиться:

- IP берётся из **последнего** элемента `X-Forwarded-For` — его дописывает сам
  Caddy. Всё, что левее, гость может прислать сам, и доверять первому элементу
  значит раздать доверие любому желающему.
- Внутренние адреса (`172.17.x`, `10.x`, `192.168.x`) в качестве IP заведения
  **отвергаются**. Через туннель или на localhost определяется именно такой
  адрес, он одинаков у всех гостей — сохранив его, заведение сделало бы
  доверенными вообще все заказы. Признак работает только на боевом домене.

Полностью закрыть дыру софтом нельзя. Что помогает физически: ламинирование
наклеек, периодический осмотр и перевыпуск токена стола — если с конкретного
стола пошёл поток фантомных заказов, один тап в `/admin/tables`, и старая ссылка
мертва.

### Счёт и чаевые

Счёт приносит официант, оплата проходит при нём. Это осознанное решение, а не
недоделка: при сценарии «оплатил в телефоне и ушёл» готовность гостей оставлять
чаевые падает с 79 % до 23 % (Toast, опрос 1 571 гостя) — личный контакт при
расчёте эту потерю снимает. Поэтому онлайн-оплаты и цифровых чаевых в продукте
нет, а на экране заказа гостю прямо написано, что счёт принесут.

Гости за столом заказывают с разных телефонов, но счёт нужен один. Заказы одного
стола собираются в **визит**: он открывается первым заказом, виден в сводке с
общей суммой и закрывается кнопкой «Счёт закрыт». Если по столу три часа ничего
не заказывали, следующий заказ откроет новый визит сам. В чат к каждому
следующему заказу бот дописывает «второй за визит, итого по столу 8 400 ₸» —
складывать в уме официант не должен.

### Меню и цены

Владелец сам меняет цены, названия, описания и категорию блюда, прячет
закончившиеся позиции в стоп-лист, добавляет и удаляет блюда и категории,
переставляет порядок тех и других и загружает фотографии с телефона. Правки
видны гостям сразу: после сохранения сбрасывается кэш гостевого меню.

У блюда и категории есть казахские название и описание. Они необязательны: меню
переводят постепенно, и позиция без перевода остаётся видимой с русским текстом,
а не превращается в пустую строку.

При большом меню категории свёрнуты, сверху есть поиск по названию — иначе
экран превращается в простыню, по которой не попасть в нужное блюдо с телефона.

Удаление — на самом деле архивирование: на блюда ссылаются позиции заказов, и
физическое удаление сломало бы историю выручки. Гость архивные позиции не
видит, в статистике прошлые заказы остаются целыми.

### Метки блюд и аллергены

Значки «Без мяса», «Острое», «Хит» и «Шеф» ставит владелец галочками в карточке
блюда. Раньше они угадывались по словам в названии и описании — и «Салат с
авокадо и креветками» уходил к гостю как веганский. Про еду догадки недопустимы:
по этой метке человек решает, можно ли ему это есть, поэтому источник теперь
только один — то, что заведение подтвердило руками.

Там же поле аллергенов («орехи, молоко, глютен») — оно видно в крупной карточке
блюда, до кнопки «Добавить». Общий текст-предупреждение внизу меню задаётся в
`/admin/settings` и выводится обычным текстом: HTML из поля ввода в разметку не
вставляется, иначе это была бы дыра на гостевом экране.

Значок называется «Без мяса», а не «Веган» намеренно: за отсутствие мяса кафе
поручиться может, за отсутствие молока и яиц в том же блюде — уже нет.

### Часы показа категорий

У категории можно задать окно («Бизнес-ланч» с 12:00 до 16:00, завтраки до
11:00). Вне окна гость её не видит, в кабинете она остаётся с пометкой времени.
Окно через полночь (22:00–02:00) считается правильно. Время местное, в поясе
заведения. Гостевое меню кэшируется 20 секунд, поэтому категория появляется и
исчезает с задержкой до 20 секунд — это нормально.

### Себестоимость и прибыль

У блюда есть поле закупочной цены; рядом сразу показывается доля себестоимости,
и она краснеет, когда переваливает за 40 %. В статистике появляются прибыль,
общий фудкост и отдельный топ «что приносит больше всего денег» — он редко
совпадает с топом по популярности.

Себестоимость фиксируется снапшотом в позиции заказа, как и цена: подорожавшая
завтра закупка не должна переписывать вчерашнюю прибыль. Блюда без заполненной
себестоимости из расчёта прибыли исключаются, а рядом с цифрой честно написано,
по какой доле проданных порций она посчитана — иначе неполные данные выглядели
бы точными.

### Заказы

`/admin/orders` — то же, что приходит в чат, но одним списком: номер, стол,
состав, сумма, пожелание гостя, кто принял на кухне и кто отнёс. Список сам
обновляется раз в 20 секунд. Заказ, до которого в чате не дошли руки, можно
отменить — кнопки в Telegram при этом гаснут, чтобы кухня не начала готовить
отменённое. Обслуженный заказ отменить нельзя: еда уже на столе.

### Вызовы официанта

`/admin/calls` — кто звал, сколько ждал и кто подошёл. Если за
`SERVICE_CALL_SLA_SECONDS` (по умолчанию 90) никто не нажал «Иду», бот дёргает
чат повторно и помечает вызов просроченным — ровно один раз на вызов. Вызовы
старше получаса не эскалируются: после простоя вываливать в чат вчерашнее
незачем. Вызов можно закрыть из кабинета, когда официант подошёл, а кнопку в
чате никто не нажал.

### Отзывы

После того как официант нажал «Обслуживаю», гость видит на экране заказа пять
звёзд. 4–5 — благодарность и ссылка на 2GIS или Google (задаётся в настройках);
1–3 — поле «что пошло не так», и жалоба сразу уходит в чат заведения с составом
заказа, столом и именами смены. Смысл именно в скорости: пока человек ещё за
столом, извиниться и исправить можно, через час это уже публичный отзыв.

Оценка одна на заказ — переголосовать нельзя. Неразобранные жалобы висят в
сводке на `/admin`, пока владелец не отметит «Разобрался». Средняя оценка за
период — там же, среди основных цифр.

### Персонал

`/admin/staff` — повара и официанты. Владелец заводит сотрудника, получает
личную ссылку в бота и пересылает её человеку; тот жмёт «Start» и начинает
получать кнопки заказов. Ссылка одноразовая, «Новая ссылка» выдаёт следующую —
на случай смены телефона.

Увольнение не удаляет запись: имя человека остаётся в статистике за прошлые
смены, а его ссылка перестаёт работать. Уволенного можно вернуть.

Кнопки заказов приходят в общий чат заведения и доступны всем, кто в нём
состоит, — поэтому уволенного нужно ещё и удалить из группы. Отметка в
кабинете сама по себе доступ не отбирает.

### Залы и столы

`/admin/tables` — зоны (Зал, Терраса, VIP) и столы внутри них. Добавить стол,
переименовать, перенести в другую зону, снять или перевыпустить его QR.
Перевыпуск нужен, когда наклейку сфотографировали и заказывают из дома: старая
ссылка умирает сразу, наклейку надо перепечатать. Снятый стол не удаляется —
прошлые заказы с него остаются в статистике, но гость по его коду получает 404.

**Заказы нумеруются внутри зоны и заново каждый день:** «Терраса №1», «Зал №1».
Сквозной идентификатор к концу месяца становится четырёхзначным — такой номер
не выкрикнешь и не сверишь на слух. Номер видят и гость на экране статуса, и
кухня в чате. Зона у заказа тоже снапшот: стол могут перевести на террасу, и
прошлые заказы не должны переехать вместе с ним.

Печать на `/admin/qr` — комплектами по зонам, с разрывом страницы между ними:
клеят их в разных залах, и разбирать общую стопку никто не станет. Два формата:

- **Наклейки** — квадраты 65×65 мм с пунктиром реза. Их ламинируют и клеят на
  стол: под плёнкой код переживает уборку, и его труднее незаметно подменить
  чужим.
- **Тейбл-тенты** — две палатки на лист. Верхняя половина печатается вверх
  ногами, после сгиба по пунктиру встаёт правильно, и код виден с обеих сторон
  стола. Плотная бумага держит форму лучше офисной.

Токенов можно печатать сколько угодно — это 96 бит энтропии плюс уникальный
индекс в базе, совпадений не будет.

Фотографии пережимаются в WebP двух размеров (160 px для списка, 800 px для
крупного показа) и лежат в томе `media`. Поворот из EXIF применяется — иначе
снимки с телефона ложились бы боком.

### Цены в меню

В карточках блюд цена печатается без «₸», а валюта названа один раз в шапке.
Меню без явной отсылки к деньгам даёт больший средний чек — в исследовании
Cornell (2007, 201 столик) убирание символа дало +8,15 % на человека. Оговорка
самого исследования: это доллары и американская аудитория, так что на тенге
эффект стоит перепроверить на своих цифрах. В корзине, итоге и на экране заказа
символ остаётся: там гость уже принял решение и сумма должна читаться
однозначно.

### Заливка меню таблицей

`/admin/menu` → «Загрузить меню таблицей». Формат CSV с колонками
`category,name,price,description,image_url`, там же кнопка скачивания шаблона.
Разбираются и выгрузки из русского Excel — с точкой с запятой и в cp1251.

Импорт двухшаговый: сначала разбор с отчётом (сколько создастся, сколько
обновится, в каких строках ошибки), и только по подтверждению — применение.
Совпадение ищется по паре «категория + название», цена и описание при этом
перезаписываются.

## Статистика

`/admin` — выручка, число заказов, средний чек, средняя оценка гостей, среднее
время от оформления до подачи, прибыль и фудкост, топ-10 блюд по продажам и
отдельно по заработку, разрез по залам, по часам и дням недели, а также работа
персонала: кто сколько заказов принял на кухне и кто сколько отнёс гостям.
Периоды — сутки, неделя, всё время. Цифры берутся из `order_status_log`, то есть
считаются по реальным нажатиям кнопок в боте.

Раздел закрыт входом по паролю. Запрос без сессии отдаёт 404, а не 403 — по
ответу не понять, что раздел вообще существует.

Для скриптов и curl остался машинный ключ: `GET /api/admin/stats?token=<ADMIN_TOKEN>&period=day|week|all`.

## Установка в реальное кафе

Локальный `docker-compose.yml` — для разработки и показа. Для боевой работы
есть отдельный стек с постоянным доменом и HTTPS: `docker-compose.prod.yml`,
`proxy/Caddyfile.prod` и `.env.prod.example`. Пошаговая инструкция с бэкапами
и обновлением — в [DEPLOY.md](DEPLOY.md).

Ключевое отличие: постоянный адрес. QR-наклейки печатаются один раз и живут,
пока живёт домен, тогда как временный адрес туннеля умирает при каждом
перезапуске.

## Языки

Гостевой интерфейс есть на русском и казахском: переключатель в шапке меню,
выбор запоминается в cookie, в адресе — `?lang=kk`. Переведены надписи
интерфейса; названия и описания блюд остаются такими, какими их ввело

## Telegram-бот

### Локально бот работает опросом

На локальном стенде `BOT_POLLING=1`, и бот сам ходит к Telegram за
обновлениями. Никакой публичный адрес для этого не нужен, и кнопки в чате
работают сразу после `docker compose up`.

Так сделано не из удобства, а по необходимости: **Telegram отказывается
принимать вебхук на адрес `*.trycloudflare.com`**. Бесплатные быстрые туннели
массово используют для фишинга, поэтому домен заблокирован целиком. Диагностика
при этом обманчива — Telegram отвечает `Bad Request: bad webhook: Failed to
resolve host`, хотя имя резолвится и с 8.8.8.8, и с 1.1.1.1, и с 9.9.9.9, а сам
адрес отдаёт 200. Если увидите эту ошибку — дело не в DNS и не в туннеле.

Со стороны это выглядит как «Telegram тормозит»: нажатие на «Принял» не доходит
до бота, тот не отвечает, и крутилка на кнопке висит до таймаута.

На проде с настоящим доменом остаётся вебхук (`BOT_POLLING=0`): он дешевле и не
держит постоянное соединение.

### Вебхук

Вебхуку нужен публичный HTTPS-адрес — тот же туннель, что и для показа.
`WEBHOOK_URL` = адрес туннеля **плюс `/api`**, потому что бэкенд живёт за
прокси:

```bash
docker compose --profile tunnel-cf up -d cloudflared
CF=$(docker compose logs cloudflared | grep -o 'https://[a-z-]*\.trycloudflare\.com' | head -1) \
  && sed -i "s|^WEBHOOK_URL=.*|WEBHOOK_URL=$CF/api|" .env \
  && docker compose up -d api        # setWebhook выполняется при старте
```

Дальше добавьте бота в группу заведения — он напишет туда свой `chat_id`,
это значение идёт в `GROUP_CHAT_ID`, после чего снова `docker compose up -d api`.
Подробности и диагностика — в [backend/README.md](backend/README.md).

`WEBHOOK_URL` можно оставить пустым: при старте приложение спросит адрес у
самого туннеля (служебный порт `cloudflared`) и переспрашивает его каждые
30 секунд, так что после перезапуска туннеля вебхук чинится сам.

### Что бот делает сам

- **Заказ** — сообщение с составом, столом и комментарием гостя, кнопки
  «Принял» → «Готово» → «Обслуживаю».
- **Напоминание** — если заказ висит непринятым дольше `ORDER_REMINDER_MINUTES`,
  бот пишет о нём повторно, один раз на заказ. Заказы старше часа
  (`ORDER_REMINDER_MAX_MINUTES`) пропускаются: после ночного простоя незачем
  вываливать в чат вчерашние.
- **Вызов официанта** — гость жмёт кнопку в меню, в чат уходит «Стол N зовёт
  официанта» с кнопкой «Иду». Повторный вызов с того же стола блокируется на
  минуту, чтобы чат не засоряли нервные тапы.

## Разработка без Docker

Docker удобен для показа, но для работы над кодом обычно быстрее поднять
только БД:

```bash
docker compose up -d db
cd backend  && uv sync && uv run alembic upgrade head && uv run uvicorn app.main:app --port 8010 --reload
cd frontend && npm install && npm run dev
```

Фронтенд при этом читает `frontend/.env.local`. Если `NEXT_PUBLIC_API_BASE`
там пустой, он работает на мок-данных и бэкенд вообще не нужен.

Если порт 3000 занят вашим `npm run dev`, контейнер `web` не поднимется —
остановите dev-сервер или задайте `WEB_PORT=3001` в `.env`.

## Что сделано и проверено

Бэкенд: меню одним запросом по токену стола, создание заказа с
идемпотентностью по `client_request_id` (проверено шестью параллельными
одинаковыми запросами — в БД одна строка), снапшоты цен и названий в позициях
заказа, поллинг статуса, инвайты персонала одноразовым токеном, бот-хендлеры
на три кнопки цикла, лог переходов статусов с защитой от недопустимых
переходов и двойных тапов.

Фронтенд: SSR-меню с липкими табами категорий, «+» прямо в списке блюд,
корзина нижней шторкой, отправка заказа и экран статуса с поллингом, который
останавливается на `served`. Сценарий в 3 тапа пройден в headless-браузере
против собранного стека; FCP на эмуляции 4G — около 1.05 с.

Не проверено вживую: кнопки в Telegram — нужен реальный `BOT_TOKEN` и
публичный HTTPS-адрес. Логика переходов статусов протестирована отдельно на
уровне сервиса.

## Что сознательно НЕ входит в MVP

Оплата и всё, что от неё зависит: разделение счёта по позициям, цифровые чаевые,
открытый чек с дозаказами. Без эквайринга это не делается.

Мультиарендность продакшн-уровня (отдельная база на заведение, поддомены),
роли owner/manager с раздельными правами, интеграции с POS и учётными системами
(iiko, Poster, 1С), ИИ-разбор накладных.

Модификаторы блюд (прожарка, топпинги, замена молока) — вместо них у заказа
одно поле пожеланий. Полные калькуляционные карты с ингредиентами, единицами
закупки и коэффициентом потерь — вместо них одно поле закупочной цены на блюдо.

Планировщик смен с прогнозом загрузки, графический конструктор схемы зала,
конструктор отчётов на OLAP-кубах, веб-экран кухни (вместо него Telegram-бот),
остальные 6 пресетов дизайн-системы.
